# Fuzzer

A fuzzer feeds a program huge volumes of mutated, unexpected inputs to find crashes — and crashes often mean exploitable memory bugs. Building your own fuzzer, run only against software you own or open-source targets in a lab, teaches you how the majority of real-world memory-safety CVEs are actually found.

## Core concepts

- **Coverage-guided fuzzing** — Instrumenting the target so the fuzzer can see which code paths each input hits, then keeping inputs that discover new paths; this is what makes AFL/libFuzzer dramatically better than blind random input.
- **Mutation vs. generation** — Mutation-based fuzzers tweak a seed corpus (bit flips, splices); generation-based fuzzers build inputs from a grammar or format spec. Mutation wins for binary formats, generation for structured text.
- **Corpus and seeds** — The starting set of valid inputs; a good seed corpus covering the format's features is often the difference between finding bugs in minutes vs. never.
- **Crash triage** — Not every crash is a vulnerability: deduplicating by stack hash, minimizing the crashing input, and running under sanitizers (ASan/UBSan) turns raw crashes into analyzable reports.
- **Sanitizers** — Compiler instrumentation (AddressSanitizer, UndefinedBehaviorSanitizer) that turns silent memory corruption into loud, precise crashes the fuzzer can detect.
- **Harness** — The small driver that feeds fuzzer-generated bytes into one library function; writing a good harness (right entry point, right scope) is most of the skill in library fuzzing.
- **Responsible scope** — Fuzz only code you own, open-source software (to report bugs upstream), or deliberately vulnerable lab targets; never point a fuzzer at someone else's running service.

## How it works

A coverage-guided fuzzer like AFL++ starts with your seed corpus and loops: pick an input, mutate it (flip bits, insert interesting values like 0xFFFFFFFF, splice two inputs), run the target, and observe. The target is compiled with instrumentation that records which basic-block edges each run covers. If a mutated input covers a new edge, it's added to the corpus as a "favorite" for that edge; if the run crashes, the input is saved for triage.

Over hours, the corpus evolves into a set of inputs that collectively explore deep into the parser — past the header checks, into the rarely-hit error paths where the bugs live. Building a miniature version (a mutator + runner + coverage bitmap over a tiny parser you wrote) makes the feedback loop tangible: you'll watch new-path discoveries compound into crashes you planted deliberately.

## Build milestones

1. Write a tiny parser with a planted bug, and build a dumb mutational fuzzer (random byte flips on seeds) that finds it.
2. Add edge-coverage feedback: instrument the parser to record visited branches, and keep only inputs that find new coverage.
3. Add a smarter mutator: dictionary tokens, arithmetic on integers, havoc + splice stages, like AFL's deterministic phases.
4. Add crash deduplication by stack hash and input minimization (shrink the crashing input while keeping the crash).
5. Harness a real open-source library (e.g., a small image or compression parser) with libFuzzer or AFL++ in a lab, and triage whatever you find responsibly.

## Best resources

- [AFL++](https://github.com/AFLplusplus/AFLplusplus) — The state-of-the-art open-source fuzzer; its docs and source are the practical bible of coverage-guided fuzzing.
- [The Fuzzing Book](https://www.fuzzingbook.org/) — A free online textbook that builds fuzzers from scratch in Python: mutation, grammars, coverage, all of it.
- [libFuzzer documentation](https://llvm.org/docs/LibFuzzer.html) — In-process fuzzing with sanitizers; the fastest way to fuzz a C/C++ library you own.
- [OSS-Fuzz by Google](https://github.com/google/oss-fuzz) — Continuous fuzzing infrastructure for open source; study its project integrations to learn harness design.

## Stretch ideas

- Write a structure-aware (grammar-based) fuzzer for a text format you invented, and compare its bug-finding rate against your mutational fuzzer.
- Build a differential fuzzer that feeds the same inputs to two implementations of one spec and flags behavioral differences.
